### 当前商业脱钩的最小完成线

1. 新本地 Git 根和实际应用不含参考产品子模块、专属功能入口、品牌/素材、源码与名称；构建不读取旧仓库。保留旧仓库作为受控证据，不删除 GitHub 历史。
2. 对已标记的直接改编嫌疑逐项给出可复核的保留许可与署名、独立替换或排除结论；现有第三方组件保留各自适用的许可/通知。无需重写没有具体疑点的全部文件，也不把自动 `pending` 台账伪造为人工批准。
3. 仓库所有者确认现有贡献、AX 标识及四语言文案的创作/授权边界；对不能确认的具体内容替换或排除。审查结果与当前提交绑定，运行 `bun run check` 和名称/快照审计后记录结论。

三项完成即可结束本轮目标，即使尚无签名包或公开下载；这只表示与参考产品的商业使用关系已厘清，**不表示正式发行已获批准**。

2026-09-26 本轮工程口径 **3/3 已完成**：独立 Git 根、源码与当前 Mac 包零命中及构建独立性已核；[固定参考候选复核](evidence/COMMERCIAL-DETACHMENT-SOURCE-TRIAGE-2026-09-26.md)记录具体保留/替换依据与包内法律文本测试；所有者确认历史贡献、AX 标识、四语言文案和四套主题的创作或授权。此完成结论只适用于当前商业脱钩目标，不能自动升级为正式商业发行、法律无侵权意见或商标可用结论。

## 1. 目标和边界

目标不是把 `legacy-prototype` 字符串批量删除，而是让新版本在**源码来源、构建、运行、产品设计和发布说明**上独立于 Legacy Prototype，同时保留 Axterm 的 Level 1 架构、安全边界和已承诺的通用终端能力。所有保留的第三方软件、字体和素材仍按各自许可证正确署名；“脱离 Legacy Prototype”不等于“没有第三方依赖”。

新仓库的完成定义：

1. 不再包含 Legacy Prototype 子模块、直接改编的 Legacy Prototype 实现、上游语言/主题快照或 Legacy Prototype 参考截图/trace；安装、测试和打包不读取 Legacy Prototype 源码。
2. Axterm 拥有独立的产品定位、视觉识别和验收场景；保留经验证好用的通用工作流，对品牌、布局细节和关键页面做有目标的优化，不再以 Legacy Prototype 1:1 或像素相似度作为发布门禁。无需为了脱钩重写所有 UI 组件。
3. 保留的功能均有独立实现或来源明确、许可相容的第三方组件；有可复核的来源与权利清单。仅把 JS 转成 TS、改名、格式化或微调代码不算独立替换。
4. 源码包、安装包及应用内可访问位置包含适用的第三方版权和许可证声明；根 `LICENSE` 仍是 Axterm 自有代码的 Apache-2.0 声明。
5. 在不含 `vendor/legacy-prototype` 的全新检出中，通过约定的代码、真实协议、桌面、打包和升级检查；重要用户数据有迁移或明确告知的退出路径。

本计划**不承诺**旧公开版本、fork、clone、缓存或历史发行物消失，也不将新版本描述为“从未参考过 Legacy Prototype”。已公开的 Apache-2.0 授权不会因删除仓库而撤销。GitHub 说明删除公开仓库不会删除已有公开 fork：<https://docs.github.com/en/pull-requests/reference/forks>。

## 4. 按依赖顺序执行

### 阶段 0：冻结、盘点与决定

1. 记录当前提交、发布包校验值、功能/协议/语言/主题清单和已有安装用户数据格式；保留一个访问受控的旧仓库与发行物备份，用于回溯和许可证举证。
2. 形成逐文件/逐包的来源台账：自有、上游改编、第三方独立库、生成数据、测试证据、字体/图标/文案；记录许可证原文、版权人、打包位置和替换策略。`AXTERM_SOURCE_FILE_REVIEW_LEDGER.json` 对准备后的源码快照逐文件固定路径、大小与哈希；`bun run source:review:worklist` 按材料类型列出所有待审文件供分派，分组不推断权利；文件变更后复核回到 `pending`。检查贡献者对 Axterm 自有代码的授权，以及新仓库预期的 Apache-2.0 声明。
3. 明确第 2 节全部取舍，记录被允许的功能变化、迁移窗口及支持平台；审查 Axterm 名称、图标和营销文案，不暗示与 Legacy Prototype 存在官方关系。

**出口：** 有经产品负责人确认的功能范围和有证据的来源台账；尚不能删除旧仓库。

### 阶段 1：先改规范，再动架构与功能

1. 新建 ADR（建议 ADR-016）明确取代 ADR-003 的 1:1 交付目标，保留 Level 1 进程、Contract、安全和资源清理不变量。
2. 经 ADR 批准后，同步改 `MASTER_SPEC`、`STATUS`、Roadmap、Matrix、`docs/README.md` 和根 README：将 122 项复刻认证改为 Axterm 自有能力/发行台账，明确旧证据的归档状态；不得把未完成项直接标记完成。
3. 为 Axterm 的渐进式 UI/UX 优化、协议、数据迁移、许可证、三平台发行建立新验收任务，并让 `bun run check` 的未来变更有可追踪依据。

**出口：** 新旧规范不冲突；旧 parity 状态可追溯，新目标有明确 owner、测试和完成门槛。

### 阶段 2：替换运行时代码和数据

1. 按 P-02、P-03 替换终端传输协议和 FTP。协议用公开规范及许可清楚的独立实现作为输入，不把上游代码逐句翻译为 TS。每个 Adapter 完成后加单元、真实协议 fixture、取消/错误/超时、限流、路径安全、打包应用测试，才移除旧实现。
2. 按 P-04、P-05 重建多语言与主题；保留 message key 的情况也要审查是否连同上游表达/编排复制。翻译来源、审校者、日期和许可形成台账。对简体中文、繁体中文、英文和日文验证 fallback、立即切换、LTR 方向和重启持久化；未来重新引入 RTL 语言须先经 ADR 并补齐对应验证。
3. 对字体、图标、品牌、截图和其他素材做独立复核；替换权利不清的内容。保留的独立第三方素材继续履行其许可证要求。

**出口：** `@legacy-prototype/*` 不在锁文件或发行依赖中；直接改编文件和上游数据快照均已替换；旧实现仅在受控归档中，产品与测试不引用它们。

### 阶段 3：兼容迁移与 Axterm UI/UX 优化

1. 按 ADR-021 立即移除旧 Legacy Prototype 数据导入/导出、`legacy-prototype://` 和旧同步格式，不发布公开迁移版。保留 Axterm 自有配置导入/导出、`axterm://`、`axterm-sync-v1`；按 ADR-023 使用全新 `data-v2/` 与 `vault-v2/`，不原位打开旧未公开原型 profile。旧本地记录保持可冷备份恢复且不触发网络活动，旧远端集合不自动删除或上传；以后的新 profile 升级仍须保护 SQLite/Vault。已有旧文件的用户只可在旧原型中手动整理后迁入 Axterm 自有格式。
2. 保留高效的终端、连接和文件工作流，在现有 React/CSS 结构上优先优化最显眼的 Shell、活动栏、导航、设置、弹窗与空态；建立 Axterm 自有品牌 token、图标、文案、页面细节和三档视口截图基线。只重构确实妨碍体验或独立品牌识别的部分，不将“全部 UI 重写”作为完成条件。
3. 移除 Legacy Prototype 像素相似度要求及参考素材，改以任务可用性、键盘、可访问名称、焦点、对比度、溢出、RTL、真实业务行为和 Axterm 自有截图回归验收。页面改色或少量美化本身不构成法律上的安全阈值；对高相似度表面、命名和宣传语仍需人工知识产权/商标审查，工程测试不能代替此审查。

**出口：** 主要工作流、故障恢复和可访问性仍通过；Axterm 品牌化与重点页面改进有设计审定记录，不以全面 UI 重写或任意像素差作为验收；旧数据的迁移或退出路径完成。

### 阶段 4：许可证、供应链与发行物

1. 保持根 `LICENSE` 为 Apache-2.0；为所有**保留**的第三方代码、数据、字体和素材生成完整、可读的 `THIRD_PARTY_NOTICES`/许可证集合，并在应用内“关于/许可证”位置与三平台安装包内提供。不得只在 README 或未打包的 `vendor` 目录放声明。
2. 输出可复核的依赖清单/SBOM、许可证扫描、来源例外和组件版本；审查直接依赖及传递依赖。检查安装包实际内容，而不只检查源码仓库。
3. 完成商业发行需要的签名/公证、正式更新源、隐私与数据处理说明、安全问题接收渠道和支持政策；这些是独立的发行任务，不因 Legacy Prototype 脱钩自动完成。正式更新源的公开 HTTPS 地址、Ed25519 公钥和发行负责人批准须写入 `UPDATE_FEED_RECORD.json` 并固定在三平台安装包内；`release:updater-feed:active-check` 未通过时不得把仅靠本地环境变量或回环夹具的更新器当作已发布服务。

**出口：** 每个平台的实际安装包均通过第三方声明、包内容、签名/更新及可运行性检查；未解决的许可或品牌问题不得通过发布门禁。

### 阶段 5：干净检出验收与新仓库切换

1. 在**不初始化 Legacy Prototype 子模块**的全新检出中执行冻结依赖安装、`bun run check`、真实协议 fixture、生产 Electron E2E、三平台打包/安装/旧版本升级测试。替换后的标准 `check` 不再调用 Legacy Prototype parity 审计；它仍需保留架构、安全、本地化及 Axterm 自有视觉门禁。
2. 审计源码、锁文件、构建脚本、文档、截图/trace 和安装包中是否仍有 Legacy Prototype 内容、引用或依赖。零字符串命中只是必要检查之一，不替代来源/相似性和许可审核。对允许保留的历史迁移文档例外逐项批准。技术脱钩和发行材料准备后运行 `bun run release:final-public:check`；它会在一次执行中运行并汇总全部前置门禁，而不是在第一个失败项停止：`migration:record:removal-check` 依据 ADR-021 与 `MIGRATION_RELEASE_RECORD.json` v2 核对所有者批准的即时移除决定，**不再要求公开迁移窗口或稳定版等待**；其余依赖版权归属、逐文件源码来源、产品标识素材、四种语言目录、公开服务与包内更新源仍须通过各自的 reviewed/active 门禁。`source:review:reviewed-check` 要求准备后源码快照中除台账自身外的每个文件都有对应字节、来源、许可证、权利人、分发位置、保留决定、依据与审查人，不能将 Git 作者字段或自动生成的 `pending` 条目当成批准。只有所有前置项均通过时，它才对准备后的整个源快照检查文件名与字节内容；输出明确说明被阻塞的门禁和最终快照是否跳过。`snapshot:final-public:check` 是其底层文字/文件名审计，可单独诊断但不能代替前者。这个组合仍不能代替最终签名安装包、三平台安装或完整法律审查。只有 `docs/` 下单个文件可通过外部批准记录例外，记录必须包含理由、审查人、日期和审批依据，且未命中的陈旧例外同样失败。此命令不进入常规 `bun run check`，因为具名审查和受控历史证据尚未处理完成。
3. 检查密钥、token、测试凭据、大型生成产物和测试 trace 不进入新仓库；保存最终测试报告、第三方许可清单、来源台账和发布物哈希。
4. 由仓库所有者从**审计后的工作树快照**创建新 Git 仓库和初始提交；不要 mirror-push 旧 Git 历史，也不要复制旧 `.git`、子模块和旧发行包。先验证新仓库的干净检出、CI、下载链接与安装包，再决定旧 GitHub 仓库是否删除。旧仓库的离线合规证据必须保存。

**出口：** 新仓库能够独立复现、测试和发布，用户升级路径有效，法律/品牌与发行负责人签收。删除旧 GitHub 仓库由所有者单独执行，不纳入自动化清理脚本。

## 5. 每个工作包的完成模板

每个 P-01 至 P-08 工作包在状态台账中记录：原来源及许可证、替换方案、新文件/依赖、功能变化、用户数据影响、测试命令、真实协议/打包证据、第三方声明位置、审查人和完成日期。任何一项未通过保持 open；不得用“文件已删除”代替产品和发行验收。

执行期间每次提交保留可运行的 Axterm 主分支或隔离工作分支。旧上游材料及对照记录可放入访问受控的证据归档，但不应不加审查地复制进新公开仓库。时间估算以阶段 0 台账为准；此前的 2–4 人月是粗略工程量，不含翻译制作、法律审查和跨平台外部证据。
