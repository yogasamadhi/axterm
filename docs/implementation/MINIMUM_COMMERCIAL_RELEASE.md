# 最小商业发行完成线

更新：2026-09-26；状态：**标准已收窄，尚未达到发行条件**。依据
[ADR-022](../adr/ADR-022-commercial-release-mac-acceptance.md)。本文件只回答
“什么时候可以结束后续商业发行任务”，不把[完整三平台任务板](REMAINING_RELEASE_WORK.md)
的 46 项逐项关闭。

> 2026-09-26 范围更新：当前目标仅为与参考产品的商业脱钩；本文件的签名、
> 公证、公开下载和发行签收条件只在将来实际商业发布时启用，不阻断当前目标。

## 范围

Axterm 继续以 Apache-2.0 开源，保留 macOS、Windows、Linux 的构建与兼容目标。
以后领取首次发行任务时，只在当前电脑验收 **macOS arm64 正式包**；Windows/Linux 原生安装和协议测试
由所有者在各自电脑自行完成，不阻断该发行任务，但未测必须标为“所有者自测待完成”，
不得写成已通过。首版采用公开 HTTPS 下载页**手动更新**，不承诺自动更新。

## 只保留四个完成条件

- [ ] **1. 内容有权发行。**所有者确认 Axterm 自有代码/贡献的授权；对已标记的
      直接改编嫌疑、来源不清的素材/翻译/主题和缺失许可声明给出保留、替换或排除决定。
      对实际分发的第三方组件保留适用许可证与版权/NOTICE，核其在源码和 Mac 包的
      About/Legal 中可读。可以使用现有清单和同来源批量证据；**不要求 958 个文件、
      62 个 native 项、260 个 WASM 项或四语言每个键逐一人工签名**。不明来源的
      高风险内容不能仅凭自动扫描或改名放行，依法需要的上游署名也不能抹掉。
- [ ] **2. Mac 包真的可交付。**从冻结源码运行 `bun run check`，构建 Mac 安装包，
      使用 Developer ID 签名并公证；从正式下载地址获取后核 SHA-256、Gatekeeper、
      独立安装/启动、核心终端/SSH/SFTP、新数据目录与 Vault 隔离、旧数据库只读拒绝、
      包内法律文本。记录源码版本、包哈希、测试结果与公证回执。已通过且未受改动
      影响的长矩阵不为凑流程重跑。Windows/Linux 构建配置不得故意破坏，但其原生
      自测结果不列入此完成条件。
- [ ] **3. 用户能正确取得和使用。**从已审定源码建立不带旧 `.git`、上游子模块、
      参考截图/trace、密钥或测试私密数据的新仓库；保留一份可读取的旧证据备份，
      不重复盘点全部历史引用。新仓库的路径、源码和 Mac 包必须通过旧名称零命中检查；
      干净检出可安装、检查并生成 Mac 包。公开
      `LICENSE`、适用的第三方声明、隐私/数据处理、安全报告方式和支持方式；同一
      发行页给出版本、说明、Mac 下载和 SHA-256，并如实说明手动更新及
      Windows/Linux 自测状态。静态仓库页面与可用联系渠道即可，不要求另建服务。
- [ ] **4. 所有者一次确认。**用一份简短记录列明上述三项证据、未解决风险、
      Mac 包哈希与 Windows/Linux“所有者自测待完成”；所有者确认后，标记
      **后续首次商业发行任务完成**。这不把完整三平台 IR 行改成 Accepted，也不授权
      自动删除旧 GitHub 仓库。

## 从后续首次发行完成线移除

不再把以下事项排成后续首次发行任务的串行前置：46 项 W/14 项 IR 全部关闭、Windows/Linux
原生结果、生产自动更新 feed、独立公网服务、每个文件/依赖/翻译键分别盖章、
全部上游 Git ref 二次清点、已过工程矩阵重复执行。
这些现有台账可作问题线索与后续完整验收资料；**该发行任务只处理真正进入新源码或
Mac 包的权利、声明、安全和可交付问题**。发现具体冲突仍须解决，不能把
`pending` 机械改为 `reviewed` 或删除测试来伪造通过。

## 最小发行检查与完整三平台门禁分开

`bun run release:minimum-commercial:check` 是后续发行任务的四条件诊断入口。它运行
迁移移除、组件/许可证文本、产品素材、四语言、旧名称和最终源码快照等八项
自动检查，再核对 `compliance/MINIMUM_COMMERCIAL_RELEASE_RECORD.json` 的
MCR-01～04 待确认模板。冻结提交后，真正的具名批准应放在不纳入源码提交的
本地发行记录，并通过
`node scripts/commercialization/check-minimum-commercial-release.mjs --check --record <external-approval.json>`
输入；否则把审批记录
和被审批提交哈希写入同一提交会形成自引用。待确认字段保持 `null`，不能为让
检查通过而填入占位值。
当前八项自动检查通过，四条完成线仍全部待证实；本地未签名包不能填入 Mac
正式交付证据。若提供完整的外部批准记录，门禁还会对本地和回下载 DMG、
`app.asar` 核 SHA-256，并实际运行 `codesign`、`spctl`、`stapler` 与 `hdiutil`
检查。公开 URL 的内容与权利结论仍需人工核其原始回执，字段检查本身不是
法律审查；只有真实下载文件才能用于回下载核验。

**冻结字节的人工核验：**从干净检出的同一提交安装依赖、运行 `bun run check`、
构建并签名；在外部审批证据中记录 `git rev-parse HEAD`、
`git status --porcelain=v1 --untracked-files=all` 的空结果、最终源码快照摘要、
构建记录及包哈希。
当前脚本比较审批记录的提交与 `HEAD`，并验证包哈希、签名和公证状态，
但**不检查工作树是否干净，也不证明安装包必由该提交构建**；发行负责人必须核对这条来源链。
`snapshot:final-public:check` 检查名称与源码卫生，不判断历史文档是否仍适合公开。
公开前应逐份排除过时迁移操作说明和受控来源审计，或留下具体的所有者保留决定；
不得为实现旧名称零命中而删除依法必须保留的版权与许可证文本。

旧 `release:final-public:check` 保留为完整三平台/自动更新路线的更严格门禁；
它的逐项台账和生产更新源要求不再作为后续首次发行的完成条件。两种检查均
不得替代 `bun run check`、真正签名安装包、公开下载实测与所有者最终确认。
