本指南为公开迁移版本准备操作说明。发布负责人必须在发布说明中填入实际的
版本号、**公开发布日期**、迁移结束日期、支持渠道与恢复说明；内部构建、测试包和
本文档日期都不会开始迁移计时。当前计划建议至少覆盖一个公开稳定版本和 90 天，取两者
较晚者，但这不是已经批准的期限。

这些发布事实必须同时写入根目录的
[`MIGRATION_RELEASE_RECORD.json`](../../compliance/MIGRATION_RELEASE_RECORD.json)。该文件当前为
`pending`，不宣布发布也不启动迁移计时。发布负责人应在公开稳定迁移版可访问后填写
版本、公开日期、不可变发行物 SHA-256、批准期限、支持范围和非敏感证据链接，并运行：

```text
bun run migration:record:active-check
```

只有该检查通过，才可将迁移窗口称为已开始。迁移期结束并准备删除兼容入口前，还必须补齐
最终稳定版本里程碑（数量必须满足批准期限）和删除批准，并运行
`bun run migration:record:removal-check`。记录拒绝未来的公开日期、未来的删除批准，且要求
每个稳定版里程碑均在首次迁移版之后、删除批准之前实际公开；里程碑必须是不同于首次迁移版
且彼此不同的后续稳定版本，移除版还必须晚于所有这些版本。版本使用稳定 SemVer；仅更改
构建元数据或日期不能重复计数。期限批准日期不得晚于首次公开迁移版，也不能填未来日期。
记录不得包含 secret、用户备份、私密支持对话或
非公开旧制品；这两个检查也不能代替旧版本、用户数据、来源权利或三平台发行证据。

迁移期内，Axterm 会继续暂时识别 Legacy Prototype 专属的数据文件、`legacy-prototype://` 会话链接和
旧同步格式；它们最终会被移除。请在升级前完成下列备份与转换。不要删除现有应用数据、
旧远端对象或旧同步 profile，直到你已验证新的 Axterm 路径可用。

## 先理解哪些数据会移动

| 数据或操作                       | 可使用的路径                                                                              | 重要边界                                                                                                                                                                                                             |
| -------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现有 Axterm 的本机升级           | 保留应用数据后正常升级                                                                    | SQLite 数据库和 application-local Credential Vault 仍是本机实时来源。Axterm 配置文件不是 Vault 备份；若改用另一台设备或新 profile，已保存的 secret 可能需要重新输入。                                                |
| Axterm 的可携配置                | “设置”中的 **Legacy Prototype / Axterm data migration** → **Export Axterm configuration** | 独立 `axterm-configuration` 文件包含连接、所有书签协议、profile、命令、自建主题、trigger 与可携设置；不包含 Vault secret、历史、AI 数据、同步 profile 或背景图片字节。用户命令与环境值仍可能含私密内容，须加密保存。 |
| 旧 Legacy Prototype 兼容数据文件 | 同一面板的 **Choose data file** / **Export data**                                         | 仅迁移期可用。导出不包含 credential secret，只报告其元数据；它也不是完整的 Axterm 备份。                                                                                                                             |
| 旧远端同步对象                   | “设置” → “同步” → **Back up remote file**                                                 | 只读保存当前同步文档；WebDAV 与原始自定义端点保留响应字节，Gist/Gitee 与命名文件容器按服务提供的 UTF-8 文本保存。不会改写、移动或删除远端对象。未启用同步加密时，副本可能含可读私密数据。                            |
| 旧同步 profile                   | “设置” → “同步” → 对应服务 → “Axterm sync format”                                         | **Back up legacy remote and create Axterm profile** 会先保存旧远端对象，再建立独立的 Axterm profile。新 profile 使用不同的远端文档/路径，且自动同步默认关闭。                                                        |

### 未公开 Axoterm 原型的首次公开版迁移边界

仓库所有者已确认旧 Axoterm/Axterm 安装包**从未公开分发**，并于 2026-09-25
批准首次公开版采用**手动迁移**：旧原型导出便携数据、自建主题逐套导出/导入，
密码在新应用重新输入；不承诺自动迁移旧 `axoterm.sqlite` 或 Vault。下列保全
`Axoterm.app` 与当前无签名 `Axterm.app` 的合成样本测试支持这项范围决定，但
不是面向真实旧用户的公开升级证据，也不能代替尚待完成的发行验收。

旧 Axoterm 样本把数据写入 `data/axoterm.sqlite`，当前 Axterm 使用
`data/axterm.sqlite`。在隔离测试中，仅将当前应用指向旧样本的同一用户数据目录
并启动，旧 SSH 主机没有自动出现；旧数据库文件仍在。**不要手工重命名或覆盖
SQLite 文件，也不要单独复制 Vault 文件**来猜测升级方式。需要保留旧原型数据
时，应先完全退出旧应用并受控冷备份其**整个**用户数据目录（包括 `data/`
与 `vault/`），不要把便携 JSON 当成密码备份。

当前已测试的显式候选路径是：旧 Axoterm UI 导出数据 JSON；若有自建主题，
在旧 UI **逐套**导出旧主题文本；当前 Axterm UI 先预览并导入 JSON，再逐套
导入主题文件，最后重新输入需要保存的密码并核对每个关键连接。旧导出的便携
JSON **不含**自建主题或测试密码；当前导入的主机 `credential_ref` 为空。
Mac 包内测试核对了两个旧包实际创建的主题在新库中的完整调色板，还验证了
一个坏主题文件被拒绝时已有两套不变；另用旧包完整冷备份恢复出主机和密码，
并在当前包验证损坏便携 JSON 与书签写入阶段失败均不留下半成品，重选完好
文件后可继续。旧包选中的已移除内置主题回退到 Axterm 默认主题；背景图片
**不在便携 JSON 中**，需从原始图片文件在新包重新选择。密码须通过新包主机
编辑器重新输入，形成新的 Vault 引用，不能复用旧 Vault 引用。
详见[限定证据](evidence/IR08-HISTORICAL-PACKAGE-UPGRADE-2026-09-23.md)。
这些是一个旧内置主题、一张合成 PNG、两套自建主题和一个晚期写入失败的
限定样本，不覆盖任意数量/形态的旧主题、图片或其他平台。范围决定不等于
这些条件已验收，也不授权删除旧目录。用户应在确认导入结果和重新输入密码前
保留完整冷备份。

当前源码的四语言迁移面板现直接提示逐项核对映射、旧便携文件可能遗漏
自建主题和背景图、逐套导出主题、保留原图片、重填缺失密码，以及核对结果前
保留完整旧数据目录备份。它是用户操作提醒，不表示应用会自动搬运旧
`axoterm.sqlite`、Vault 或背景图片；最终公开包仍须复核这段提示。

已验证的历史源码包 `657b3cc` 的旧 **Export data** 文件不包含用户自建终端主题；
它不能代替完整数据目录冷备份。先保留整个旧 profile（包含数据库和 Vault），在当前
迁移版本中确认自建主题仍可见，再使用当前版本的 **Export Axterm configuration**
生成包含自建主题的可携配置。macOS 工程测试已将该配置导入全新 profile，核对终端
和界面配色保持一致；但可携配置仍不含 Vault secret。这个结论只针对已测试的历史包，
不代表所有旧发行版的导出格式均相同。

两种便携文件路径的单文件上限均为 16 MiB。迁移期的 Legacy Prototype 兼容导入与导出现在使用相同的大小上限；文件在 8–16 MiB 之间不会仅因导入器原先较小的限制而被拒绝。大小限制不代表所有旧字段都能转换，提交前仍须检查逐项映射报告。

### 需要保留本机凭据时：冷备份整个应用数据目录

Axterm 目前没有一键完整本机备份。若需保留已保存的 SSH/同步凭据或准备回退升级，先完全退出
Axterm（包括后台实例），再将**整个**应用数据目录复制到加密、受访问控制的备份位置；不要只复制
`data/axterm.sqlite` 或导出的 JSON。默认正式版的位置通常是 macOS 的
`~/Library/Application Support/Axterm`、Windows 的 `%APPDATA%\Axterm`、Linux 的
`${XDG_CONFIG_HOME:-~/.config}/Axterm`；若使用了自定义 `--user-data-dir`，应备份该自定义
目录，以实际安装的 `userData` 路径为准。

备份至少要完整保留 `data/`（包括数据库及相关文件）、`vault/`（尤其是 `master.key`、
`metadata.json` 和凭据文件），以及同目录中的其他 Axterm 状态。Vault 的主密钥与加密凭据
**同时存在于这份副本中**，因此整个副本都是高敏感数据：不要提交到 Git、放入公开网盘、
发送给支持人员或当成普通配置文件分享。复制完成后，在 Axterm 仍关闭时核对源与副本的
文件清单/哈希；恢复时先保留当前目录，再把完整副本放到目标应用数据位置，启动 Axterm，
实际检查关键连接和同步 profile。不要把迁移自动生成的
`axterm.sqlite.pre-migration-34.bak` 当作完整备份：它只保护当时的数据库，不包含 Vault。

当前工程验证已用历史版本生成的完整数据目录做冷备份，在另一个目录恢复并启动当前打包版，
核对 SQLite 迁移、关联记录和三个 Vault 凭据均可读取；这不等于已验证真实用户备份、
跨设备恢复或 Windows/Linux 安装版，公开发布前仍须补齐相应证据。

## 推荐迁移顺序

### 1. 保护当前 Axterm 安装

1. 退出 Axterm；如需保留凭据或回退升级，按上面的冷备份步骤复制**完整**应用数据目录，
   保留 application-local Vault，确认副本受保护后再启动 Axterm。
2. 打开“设置”中的 **Legacy Prototype / Axterm data migration**，选择 **Export Axterm configuration**，
   将生成的文件保存到受保护的位置。
3. 如需核对另一台设备或恢复前的文件，先选择 **Inspect Axterm file**。该操作只校验格式、
   引用与 ID 冲突，不写入本机数据。
4. 只有在检查结果符合预期时才选择 **Import Axterm configuration**。预览会列出将创建、
   不变、冲突和保留的条目；发生冲突或无效引用时，先修正文件或本机数据，不要提交。
5. 默认导入只创建可携连接和用户内容。只有确实要覆盖保存的外观、布局、终端、文件与
   快捷键设置时，才勾选恢复可携设置。当前工作区保持打开，导入的工作区布局在下一次完整
   启动时生效；隐私选择、依赖 credential 的代理设置和 Vault 始终保留在本机。

导入在一次 SQLite 事务中提交：任一条目写入失败时，前面的配置条目也不会部分落盘。
预览有有效期；过期或本机数据变化后，应重新选择文件并重新预览。

### 2. 导入旧 Legacy Prototype 兼容数据时逐项核对

1. 在同一迁移面板选择 **Choose data file**，选择旧 JSON 导出文件。
2. 先阅读映射报告，而不是立即导入。报告会分别标记 `Will create`、`Unchanged` 和
   `Skip`，每项还会列出已映射及未映射字段。
3. 当前导入器识别 SSH、Local、Telnet、Serial、RDP、VNC、FTP、SPICE 和 Web 书签形状。
   另外，工程测试现在有一份仅保留七种非 SSH 书签的脱敏样例，派生自 Legacy Prototype v1.101.16
   官方桌面包的实际 UI 导出；它不是完整旧数据文件，也不能代表其他 Legacy Prototype 版本。
   该版本 UI 允许保存空用户名的 RDP 书签，但 Axterm 目前要求 RDP 用户名，所以这类记录会在
   预览中显示 `Skip` 和具体原因，而不是到提交时才失败。SPICE 仍由公开字段参考和合成样例
   覆盖，尚无该版本的实际导出样例。不能据此保证你的每个旧字段都能转换。逐项映射报告才是本次
   文件的实际结果：未映射字段不会导入，不支持的记录可能显示为 `Skip`。旧
   `runScripts` 会明确省略，绝不会执行。
4. 确认所有预期结果后，才执行导入。提交会再次检查书签树、设置和窗口偏好的版本，冲突
   不会被自动重放。
5. 仅有类型、标签和时间等信息的 `credentialMetadata` 只是凭据清单，不含 secret，不能
   重建旧 Vault。若所选文件本身确实包含受支持的内嵌密码、代理密码、SSH 私钥或证书值，
   导入器会将相应值直接写入 Axterm application-local Vault；这些值不出现在预览或产品
   SQLite 中，也不会保留为旧 Vault 引用。若文件只有凭据元数据或不含某项凭据，就必须在
   Axterm 的受控凭据界面重新输入。导入后仍应逐台验证关键连接。由于来源文件可能含有内嵌
   secret，请按敏感文件保护，不要上传、提交到 Git 或发送给支持人员。

保留原始 JSON 文件直至你已实际连接每个关键主机、运行关键命令并检查配置；它既不是
Vault 备份，也不能证明所有旧功能和字段都已转换。

### 3. 迁移远端同步，而不覆盖旧对象

1. 打开“设置” → “同步”，选择旧 **Legacy migration format** profile 对应的服务。
2. 先点击 **Back up remote file**，将远端文件保存到受保护位置，并记录界面返回的
   SHA-256。该操作不会修改远端对象。
3. 切到 **Axterm sync format**。若尚无 Axterm profile，选择
   **Back up legacy remote and create Axterm profile**，再次选择安全的本地备份位置。
4. 确认成功消息显示旧远端备份和 SHA-256。新 profile 与旧 profile 并存，使用独立的
   Axterm 文档和远端位置；旧 profile、旧路径和旧远端对象会保留。
5. 新 profile 的自动同步默认关闭。先保存/检查 profile，执行 **Compare**，再由用户明确
   选择 **Upload** 或 **Download**。下载只产生预览；先审阅结果，才显式提交。
6. 在另一台设备验证新的 Axterm profile 后，仍保留旧 profile 与本地备份，直至发布说明中
   的迁移期结束。不要把远端同步文件当作完整本机/Vault 备份。

**GitHub Gist 截断例外：** GitHub 的 Gist REST API 每个文件最多返回 1 MB 内容；文件列表
超过 300 个条目时也会被截断。超过 10 MB 的文件或被截断的完整文件列表需要克隆 Gist
才能确保取得完整内容。当前 Axterm 会尝试经过校验的 raw URL，并核对返回字节数与远端文件
大小；但尚未实现 Git 克隆。如果应用内备份提示需要克隆，请不要删除旧 profile、覆盖 Gist 或
继续切换同步源。可用 GitHub Desktop 或可信任的 Git 客户端，将该 Gist 的 HTTPS 克隆 URL
克隆到一个新的私有本地目录，再把当前版本中实际使用的同步文件复制到另一个受保护的备份
位置并记录文件大小与 SHA-256。Gist 克隆 URL 应按敏感信息保护；不要分享 URL/克隆目录，
也不要向原 Gist 推送改动。官方限制说明见
[GitHub Gist truncation 文档](https://docs.github.com/en/rest/gists/gists#truncation)。
这是应用内备份失败时的手动恢复路径，不代表 Axterm 已自动支持 Git 克隆或关闭 IR-08。

**Gitee Gist 截断例外：** 若 Gitee 返回不完整的 Gist 文件，Axterm 会拒绝读取和备份，
不会依赖未经验证的 `raw_url`，也不会修改远端对象。请保留旧 profile 与远端文件；通过
可信途径取得**完整**旧同步文件并核对文件大小和 SHA-256 后，才能继续迁移。若无法确认
备份完整，就停止切换并联系发布说明中的支持渠道，不要用不完整的 API 响应覆盖旧文件。
这里不承诺 Gitee 有与 GitHub 相同的克隆或 raw-file 恢复行为。

若旧远端文件启用了加密，保留能访问旧 profile 所需的本机凭据和恢复信息；若未加密，按
敏感文件保护备份副本。迁移操作不会为了“清理”而删除任何远端用户数据。

### 4. 更新会话链接和命令行自动化

`legacy-prototype://` 只在迁移期内解析。对于不含密码或 token 的链接，将前缀替换为
`axterm://`，保留其余连接参数，然后在迁移版本中实际打开并核对预填的协议、主机、端口、
用户名与标题。不要把 secret、私钥口令或长期 token 放入链接；即使当前版本把 URL 密码
仅用于一次会话，也应改用本机 Vault 或交互式输入。

旧的 `--batch-op` workflow 数组同样只在迁移期提供受限转换：它只允许一个初始 SSH
连接和有限的命令步骤，内联凭据会被丢弃，文件传输需要另行 File Grant。请把持续使用的
自动化改为 Axterm 原生的有界操作文档，并在受控测试环境验证结果；不要依赖旧数组在迁移
期结束后继续执行。

## 出现问题时

- 预览显示冲突、跳过或映射异常：取消预览，保留原文件和 SHA-256，先修正或手动重建。
- 导入提交报错：它应当原子回滚；重新打开 Axterm 后检查本机数据，再重新生成预览。
- 新同步 profile 无法使用：停止自动同步，使用保留的旧 profile 与本地远端备份恢复，不要
  删除旧远端对象。
- 需要回退本机升级：退出 Axterm，保留当前目录，使用升级前的**完整冷备份**和对应版本
  的安装包做受控恢复；只有便携配置文件或自动数据库回滚副本时，Vault 凭据可能无法恢复，
  不要把它们描述为完整系统备份。尤其不要将便携
  配置文件描述为包含 Vault secret 的完整系统备份。

发布说明必须给出与该版本对应的支持渠道、受支持平台和恢复步骤。本草案不会替代真实旧
版本升级测试、Windows/Linux 已安装应用证据、真实 provider 测试或发布负责人的迁移期签收。
